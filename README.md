# Showtakes

Ratings, reviews, and discussion of theatre productions: Letterboxd for the stage.

- Domain language: [CONTEXT.md](CONTEXT.md)
- Architecture decisions: [docs/adr/](docs/adr/)
- Ordered work list: [docs/TASKS.md](docs/TASKS.md)

## Requirements

- Node.js 24 or newer
- pnpm (version pinned in `package.json`)
- OrbStack (or another Docker runtime) for the local Postgres database and
  Mailpit email inbox

## Getting started

```sh
pnpm install
pnpm exec playwright install chromium   # once, for browser tests
cp .env.example .env                    # once, local settings
pnpm services:up                        # start Postgres and Mailpit
pnpm db:migrate                         # create or update the tables
pnpm dev                                # http://localhost:3000
```

## Commands

| Command              | What it does                                             |
| -------------------- | -------------------------------------------------------- |
| `pnpm dev`           | Run the site locally with live reload                    |
| `pnpm build`         | Production build                                         |
| `pnpm lint`          | Code checks, including the `src/core` import rules       |
| `pnpm typecheck`     | TypeScript type checking                                 |
| `pnpm test`          | Unit and integration tests (Vitest; needs `services:up`) |
| `pnpm test:unit`     | Unit tests only, no database needed                      |
| `pnpm test:e2e`      | Browser tests (Playwright)                               |
| `pnpm services:up`   | Start local Postgres and the Mailpit inbox               |
| `pnpm services:down` | Stop them (database data is kept in a Docker volume)     |
| `pnpm db:generate`   | Write a SQL migration from changes to any `schema.ts`    |
| `pnpm db:migrate`    | Apply pending migrations to `DATABASE_URL`               |
| `pnpm db:studio`     | Browse the database in Drizzle Studio                    |
| `pnpm admin:promote` | Make a signed-up Member an Admin: `... you@example.com`  |

### Database tests

Files named `*.integration.test.ts` run against a throwaway database that
each `pnpm test` run creates, migrates, and drops (`src/db/testing/`). Test
files share it and run in parallel, so each test creates its own uniquely
named data, deletes it afterwards, and never assumes a table is empty.

To inspect what a failing test left behind, run `KEEP_TEST_DB=1 pnpm test`;
the database is kept and its name printed. Test databases older than a day,
including ones left by killed runs, are dropped at the start of each run.

Integration tests build the whole site (database, Better Auth, operations)
with `createTestServices()` from `src/wiring/testing/`, the same wiring the
web app uses.

Browser tests (`pnpm test:e2e`) use a separate database, `showtakes_e2e`,
which they create and migrate themselves, and read emails from Mailpit.

### Business rules and operations

`src/core/` holds everything the site does, independent of the web pages
(ADR 0002, ADR 0004). It has one folder per section of [CONTEXT.md](CONTEXT.md)
(`people/`, later `catalog/` and `opinions/`), plus `shared/` for the Actor,
permission checks, the Result type, and the Logger interface. Pages and
server actions reach it only through `getOperations()` in
`src/server/operations.ts`, which builds `createOperations()` from
`src/core/operations.ts` for the current request.

File names say what a file may do, and lint enforces it:

| File                         | Contents                                   |
| ---------------------------- | ------------------------------------------ |
| `<concept>.operations.ts`    | Operations; may use the database           |
| `schema.ts`                  | The area's tables                          |
| any other `.ts`              | Pure rules; no database imports allowed    |
| `*.test.ts`                  | Unit tests, no database                    |
| `*.integration.test.ts`      | Tests against the throwaway test database  |

An operation takes the Actor first. A permission refusal (something a correct
page never offers) throws `PermissionRefusedError`; an expected failure
(something a person can cause through a correct page) is returned as a
`Result`. `src/core/people/allowlist.operations.ts` is the reference example.

### Email

Code that sends email receives a `Mailer` (`src/mail/mailer.ts`) and does not
know who delivers it. `MAIL_PROVIDER` chooses the adapter and must be set:

- `mailpit` (development and tests): every email goes to the local Mailpit
  inbox at http://localhost:8025 and is delivered to nobody.
- `resend` (production): real delivery through Resend, using
  `RESEND_API_KEY`. Set up in the first deploy.

Integration tests check sent mail through `src/mail/testing/mailpit-inbox.ts`,
each using its own unique recipient address.

### Logging

Events are written as one JSON line each through a `Logger`
(`src/core/shared/logger.ts`, ADR 0006): successes at `info`, refusals and
failed logins at `warn`, faults at `error`. Every event name is listed in
that file. Lines carry the email involved and where the request came from
(IP address, user agent, request id); passwords, tokens, and cookies are
always redacted.

- `LOG_LEVEL` (required) sets the quietest level written. `warn` hides
  successes.
- `LOG_FILE` also writes every line to a file. `.env.example` sets
  `logs/showtakes.log`, which is not committed; the browser tests' server
  writes `logs/e2e.log`. Production leaves it unset and sends standard
  output to a log service.

To follow the log while developing: `tail -f logs/showtakes.log`. Tests
check what was logged with `services.logger.entries` from
`createTestServices()`.

### Accounts and logins

Better Auth (`src/auth/auth.ts`) keeps Members and their logins in our
database and serves its endpoints at `/api/auth/*`. Logging in, logging out,
email verification, and password reset pages call it directly from the
browser (`src/auth/client.ts`); signup goes through
`operations.accounts.signUp`, which applies the invite allowlist and handle
rules first (ADR 0005).

To try it locally: add your email to the allowlist (for now,
`pnpm db:studio` or SQL; the admin screen comes with the "Admin: members and
allowlist" ticket), sign up at http://localhost:3000/signup, and open the
verification email in Mailpit at http://localhost:8025.

### Roles and scripts

A Member may be a Curator, an Admin, both, or neither (CONTEXT.md). Roles
are rows in the `member_role` table, read into the Actor on every request,
so a change takes effect on the Member's next page. To make yourself the
first Admin, sign up, then run `pnpm admin:promote you@example.com`.

Scripts in `scripts/` run with `tsx` and act as the operator (ADR 0007):
they call the same operations as the site, which let the operator through
wherever an Admin may act. Web code can never act as the operator; lint and
the permission checks both refuse it.

### Generated shadcn/ui code

`src/shadcn/` holds everything the shadcn/ui installer generates
(`pnpm dlx shadcn add <component>`); `components.json` points the installer
there. Keeping it separate marks which code we did not write, so it is exempt
from the project's commenting conventions and can be compared with newer
shadcn releases. It is still ours to edit: restyle these files freely. App code
should normally use our wrappers in `src/components/` rather than importing
from `src/shadcn/` directly.
